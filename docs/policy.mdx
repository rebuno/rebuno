---
title: "Policy"
description: "The YAML rule language for allow, deny, and require-approval"
---

Policy decides which effects an agent may perform. Each agent has its own rule
bundle, evaluated the first time a step is submitted. A rule returns `allow`,
`deny`, or `require_approval`.

A replayed step returns its recorded outcome without consulting policy again, so
editing a bundle does not re-gate work an execution has already done.

Attach a bundle inline with `policy:` or from a file with `policy_file:` in a
provisioning manifest. Set one or the other, not both, and write the
`policy_file` path relative to the manifest. You can also load a bundle over the
admin API with `POST /v0/policies/{agent_id}`.

The kernel compiles a bundle before storing it, so a malformed one is rejected
with a validation error at registration rather than failing later at a step. An
agent with no bundle is unrestricted, in production as much as in dev.

## Bundle format

```yaml
default_action: deny        # allow | deny (default: deny)
rules:
  - id: allow-llm
    when:
      step_kind: llm_call
    then:
      decision: allow

  - id: allow-research-tools
    when:
      targets: ["web_search", "doc_fetch", "calculator"]
    then:
      decision: allow
      reason: research tools are permitted
```

## Evaluation

Rules are evaluated top to bottom in the order they appear in the bundle. The
first rule whose `when` block matches wins, so put the specific rules above the
broad ones. If nothing matches, `default_action` applies, and any value other
than `allow` means deny. Every rule needs an `id`, unique within the bundle.
Unknown keys are rejected, so a bundle carrying a key no rule field claims will
not load.

`default_action` covers `tool_call` and `llm_call` steps. An unmatched `local`
step is allowed whatever `default_action` says. To govern one, match it with a
rule on `target` or `step_kind: local`.

## Match conditions

All fields present in a rule's `when` block must match (AND). Omitted fields are
not checked.

| Field | Matches |
|-------|---------|
| `target` | The step target (tool name or model id). Supports glob patterns in Go's `path.Match` syntax (`web_*`, `mcp/*`), where `*` and `?` match any character including `/`. Malformed patterns fail at load. |
| `targets` | A list of targets/globs; matches if any matches. |
| `agent_id` | The submitting agent's id. |
| `agent_ids` | A list of agent ids; matches if the agent is in it. |
| `step_kind` | `tool_call`, `llm_call`, or `local`. |
| `arguments` | Predicates against fields inside the call's JSON arguments. See [Argument predicates](#argument-predicates). |
| `history` | Clauses about steps policy allowed earlier. See [History conditions](#history-conditions). |

### Argument predicates

`arguments` is a map of argument key to predicate. The key must be present in
the call's arguments, and every constraint listed under it must pass. Values are
compared as strings.

A predicate needs at least one constraint. An empty one (`command: {}`, or
`command: {equals: ""}`) is rejected at load, because a constraint that matches
any value would silently widen the rule.

```yaml
when:
  target: shell_exec
  arguments:
    command:
      regex: '^\s*(ls|cat|pwd|echo|whoami|date)(\s+[^;&|<>$`()\\]*)?\s*$'
```

| Constraint | Passes when the value… |
|------------|------------------------|
| `equals` | equals the string exactly |
| `contains` | contains the substring |
| `one_of` | is one of the listed strings |
| `regex` | matches the RE2 regular expression |
| `equals_arg` | equals the argument at this key of the call being decided. Only valid in [history clauses](#history-conditions). |

A key with dots is a path into nested objects, so `config.environment` reads
`environment` inside the `config` object. The rule does not match when a
segment is missing or its value is not an object; arrays are not traversed. An
argument whose own name contains a dot takes precedence over the path it spells.

```yaml
when:
  target: deploy
  arguments:
    config.environment:
      equals: staging
```

A value that is not a string, such as a number or an object, is compared as
compact JSON text: `{"force": true}` compares as `{"force":true}`.

### History conditions

`history` is a list of clauses about the steps policy allowed earlier: steps that
started, whether they succeeded, failed, or are still running. Every clause must
hold.

```yaml
  - id: refund-after-lookup
    when:
      target: issue_refund
      history:
        - target: lookup_order
          within: 1h
          arguments:
            order_id:
              equals_arg: order_id
          result:
            status:
              equals: delivered
        - target: verify_customer
          arguments:
            customer_id:
              equals_arg: customer_id
    then:
      decision: allow
```

| Field | Meaning |
|-------|---------|
| `target`, `targets`, `step_kind`, `arguments` | Select earlier steps, as in a rule's `when` block. `equals_arg` compares an argument with the call being decided. |
| `result` | Predicates against fields of the step's JSON result. Only succeeded steps match. |
| `scope` | `execution` (default) or `session`. `session` reads every execution in the session, and falls back to the execution for one without a session. |
| `within` | A Go duration. Only steps started that recently count. Omit it to read the whole scope. |
| `sum` | An argument to add up across the selected steps. |
| `distinct` | An argument whose distinct values are counted. |
| `at_least`, `at_most` | Bounds on the count of selected steps, or on the `sum` or `distinct` total. Without either, `at_least: 1`. |

The call being decided counts toward a clause it matches, unless the clause has
`result`. A clause with `at_most: 3` on its own target allows the third call and
refuses the fourth, and a `sum` includes the amount being requested. Steps still
running count, so parallel calls cannot pass a cap before earlier ones finish.
Denied steps and steps awaiting approval do not count.

A clause with the default bound requires that something happened; `at_most: 0`
requires that it did not. Either can carry the decision:

```yaml
  - id: no-email-after-fetch
    when:
      target: send_email
      history:
        - target: web_fetch
          scope: session
    then:
      decision: deny
      reason: the session has read untrusted web content
```

A selected step whose `sum` argument is missing or not a number fails the
clause. Write a cap as an `allow` rule above a stricter one, so such a step
falls through to the stricter rule:

```yaml
  - id: transfer-under-cap
    when:
      target: transfer
      history:
        - target: transfer
          scope: session
          within: 24h
          sum: amount
          at_most: 5000
    then:
      decision: allow
  - id: transfer-over-cap
    when:
      target: transfer
    then:
      decision: require_approval
```

If the kernel cannot read history, the step is denied with reason
`history_unavailable` under the rule being evaluated.

The client names the session, so a new session starts with empty history. A
session-scoped count or sum therefore limits a cooperating client; for a hard
ceiling, use a [rate limit](#rate-limits) with `per_what: agent` or `global`. A
clause that requires something to have happened denies in a new session.

## Rule decisions

A rule's `then` block carries the decision and its options:

| Field | Meaning |
|-------|---------|
| `decision` | `allow`, `deny`, `require_approval`, or `judge`. Required. |
| `reason` | Human-readable explanation. Recorded in the decision event and returned on deny. |
| `approval_config` | Who approves, and for how long. Only meaningful with `require_approval`. See [Approvals](#approvals). |
| `rate_limit` | Caps how often the rule may fire. See [Rate limits](#rate-limits). |
| `budget` | Caps the LLM tokens the execution may spend. See [Token budgets](#token-budgets). |
| `judge` | How a model decides the call. Only valid with `judge`. See [Judge](#judge). |

Every policy decision event (`step.allowed`, `step.denied`,
`step.awaiting_approval`) carries the matched `rule_id` in its payload, which is
what makes the log auditable. `rule_id` is the matched rule's own `id` and is
not settable from the bundle. A decision that came from somewhere other than a
rule gets a fixed id. The `default_action` fallthrough is `default`, an
unmatched local step is `local`, an agent with no bundle is `permissive`, and a
stored bundle that will not compile is `bundle-error`.

### Approvals

When a rule returns `require_approval`, the kernel records
`step.awaiting_approval` and `approval.requested`, creates an approval, and
moves the execution to `blocked`. A human grants or denies it through the
approvals API and the execution resumes. See [Events](/events) and
[Approvals](/api#approvals).

```yaml
  - id: approve-fs-writes
    when:
      targets: ["fs_write_*", "fs_edit_*"]
    then:
      decision: require_approval
      reason: filesystem writes need approval
      approval_config:
        approvers: ["alice", "bob"]   # omit to let anyone decide
        timeout: 5m                   # default: the kernel's DefaultApprovalTimeout
        message: check the target path before granting
```

| Field | Meaning |
|-------|---------|
| `approvers` | Who may grant or deny. A decision whose `decided_by` is not in the list is rejected with `403 forbidden`. Omit the field, or leave it empty, to let anyone decide. That is the default. |
| `timeout` | A Go duration (`30s`, `5m`, `1h30m`). The approval expires after it. Defaults to the kernel's configured timeout. |
| `message` | Shown to whoever resolves the approval. |

`decided_by` is the authenticated caller: `admin` for the deployment token, or
`service:<key id>` for an API key. A caller holding the `approvals:delegate`
scope may name the approver instead, and the approval records that caller in
`asserted_by`. `approvers` entries match either form.

### Rate limits

A rule can cap how often it fires. The bucket is keyed on the rule's `rule_id`
and the scope in `per_what`, so two rules never share one.

```yaml
  - id: limit-search
    when:
      target: web_search
    then:
      decision: allow
      rate_limit:
        max_calls: 5
        window: 1m
        per_what: execution      # execution (default) | session | agent | global
        max_wait: 5m             # unset (default) refuses instead of waiting
        on_limiter_error: allow  # allow (default, fail-open) | deny (fail-closed)
```

`per_what: session` shares the bucket across a session's executions, and falls
back to the execution for one without a session.

A step over the limit comes back as `rate_limited` rather than a policy denial.
Put a hard ceiling in a `deny` or `require_approval` rule instead.

With `max_wait` set, a limited step parks. The submit returns `blocked`, the
execution stays `running`, and the kernel re-dispatches once the bucket refills.
An execution parks only once. If the step is still over the limit on the retry,
or the wait would run longer than `max_wait`, it is refused.

### Token budgets

A rule can cap the LLM tokens an execution or a session spends. The cap applies
only to a rule that decides `allow`.

```yaml
  - id: cap-llm-spend
    when: { step_kind: llm_call }
    then:
      decision: allow
      budget:
        max_tokens: 200000
        scope: execution       # execution (default) | session
        on_exceed: deny        # deny (default) | require_approval
```

The meter sums the input and output tokens recorded on the execution's steps, so
an effect counts once however many times it was attempted. With `scope: session`
it sums every execution in the session, including failed ones, and falls back to
the execution for one without a session. Only `llm_call` steps
record usage, so nothing else moves the meter.

The check runs before the call, so the step that crosses the limit still runs. A
response with no parseable usage never advances the meter, most often an
OpenAI-style stream requested without `stream_options.include_usage`, and
`rebuno_llm_usage_missing_total` counts those. If the kernel cannot read the
execution's usage at all, it lets the step through.

### Judge

A rule that decides `judge` hands the call to a decision model, which picks
`allow`, `deny`, or `require_approval`. It suits tools whose calls are too varied
to list as predicates, such as a shell. Text in the arguments can steer the
model, so put `deny` rules for commands known to be dangerous above it.

```yaml
  - id: deny-rm-root
    when:
      target: bash
      arguments:
        command:
          regex: 'rm\s+-rf\s+/(\s|$)'
    then:
      decision: deny

  - id: judge-bash
    when:
      target: bash
    then:
      decision: judge
      judge:
        instructions: commands run in a disposable build container
        criteria:
          allow: Reads files or runs builds and tests inside the workspace.
          deny: Reaches the network or writes outside the workspace.
          require_approval: Installs packages or changes the container's configuration.
        threshold: 0.6              # default 0.6
        fallback: require_approval  # allow | deny | require_approval (default)
      approval_config:
        approvers: ["ops"]
```

| Field | Meaning |
|-------|---------|
| `question` | The question the model answers about the call. Optional. |
| `criteria` | Descriptions of when `allow`, `deny`, and `require_approval` apply, keyed by decision. The model scores all three; a decision left out keeps its default description. Optional. |
| `instructions` | Context about where the call runs, passed to the model with it. Optional. |
| `threshold` | The probability, from 0 to 1, the model's top choice needs to stand. Default `0.6`. |
| `fallback` | The decision when no choice reaches `threshold`, or when the model cannot be reached. Default `require_approval`. |

Without `question`, the model answers: "Should `tool_call` run automatically, be
blocked, or wait for a human to approve it?" The default criteria are:

| Decision | Default description |
|----------|---------------------|
| `allow` | Safe to run unattended: a routine action whose effects are easy to undo or minor if unwanted. |
| `deny` | Harmful in any context: destroys data, exposes secrets, or runs untrusted code. |
| `require_approval` | Possibly fine, but consequential or hard to undo, so a human should confirm. |

The model is any HTTP API that returns a probability for each decision. A YAML
file named by `REBUNO_JUDGE_CONFIG` ([Deployment](/deployment#configuration))
describes the request and where the probabilities are in the response. Without
it, `judge` rules deny.

```yaml
url: https://api.typesafe.ai/v1/systemone
headers:
  Authorization: Bearer ${TYPESAFE_API_KEY}
body: |
  {
    "model": "jev-latest",
    "state": {"tool_call": {{json .ToolCall}}},
    "questions": {
      "decision": {
        "type": "choice",
        "instructions": {{if .Instructions}}{"question": {{json .Question}}, "note": {{json .Instructions}}}{{else}}{{json .Question}}{{end}},
        "criteria": {{json .Criteria}}
      }
    }
  }
probabilities: answers.decision.probabilities
timeout: 5s
```

| Field | Meaning |
|-------|---------|
| `url` | Endpoint the kernel POSTs to. `${VAR}` expands from the environment. |
| `headers` | Request headers. `${VAR}` expands from the environment. |
| `body` | Go [text/template](https://pkg.go.dev/text/template) for the JSON request body. `json` encodes a value. |
| `probabilities` | Dot-separated path in the response to an object mapping `allow`, `deny`, and `require_approval` to probabilities. Array elements are addressed by index. |
| `timeout` | Request timeout. Default `5s`. |

The body template receives:

| Value | Content |
|-------|---------|
| `.ToolCall` | `agent_id`, `tool`, and `arguments` of the call. |
| `.Question` | The rule's `question`, or the default question. |
| `.Criteria` | Each decision mapped to a description of when it applies, with the rule's `criteria` in place of the defaults. |
| `.Instructions` | The rule's `instructions`, or empty. |

[`examples/judges`](https://github.com/rebuno/rebuno/tree/main/examples/judges)
holds provider configs.

## Testing a bundle

`rebuno policy test` evaluates a bundle against cases and exits non-zero when a
decision does not match what the case expects.

```bash
rebuno policy test examples/policies/shell.yaml
```

Cases live beside the bundle, `shell.yaml` with `shell.policytest.yaml`, or
wherever `--cases` points.

```yaml
agent_id: shell             # inherited by cases that do not name one
cases:
  - name: read-only command
    target: shell_exec
    args: { command: "ls -la /tmp" }
    expect: allow
    expect_rule: allow-safe-shell
  - name: chained command
    target: shell_exec
    args: { command: "ls /tmp; rm -rf /" }
    expect: require_approval
```

`target` is required and `kind` defaults to `tool_call`. `expect` is the
decision the case must produce and `expect_rule` the rule that must make it,
which catches a case still decided correctly but by the wrong rule. Omit both to
assert nothing. Unknown keys are rejected. A run also lists the rules no case
reached, which is how a rule shadowed by a broader one above it shows up.

`history` lists the allowed steps a case sees in every scope. Each takes
`target`, `kind`, `args`, `result`, and `ago`, a Go duration before the decision:

```yaml
  - name: email after fetch
    target: send_email
    history:
      - target: web_fetch
        ago: 10m
    expect: deny
```

`--target <name> --args '{...}'` probes a single input instead of running cases,
printing its decision and rule.

A finished execution is the other source of cases. Replaying one feeds its
recorded steps back through a bundle and fails the steps a change would now
decide differently. The steps come from a running kernel, so replay names an
agent with `--agent-id` and reaches a kernel the way every command does
([CLI](/cli)), or calls
[`POST /v0/policies/{agent_id}/test`](/api#policy) directly. Each replayed step
sees the history of its execution and session as it stood when it was decided.

```bash
rebuno policy test shell.yaml --execution <id> --agent-id shell
```

`--session`, `--since`, and `--limit` replay many of the agent's executions at
once, newest first, 100 by default and at most 1000:

```bash
rebuno policy test shell.yaml --agent-id shell --since 7d
```

## Examples

**Deny by default, allow only known tools:**

```yaml
default_action: deny
rules:
  - id: allow-llm
    when: { step_kind: llm_call }
    then: { decision: allow }
  - id: allow-tools
    when: { targets: ["web_search", "calculator"] }
    then: { decision: allow }
```

**Allow safe shell commands, gate the rest on approval:**

```yaml
default_action: deny
rules:
  - id: allow-llm
    when: { step_kind: llm_call }
    then: { decision: allow }
  - id: allow-safe-shell
    when:
      target: shell_exec
      arguments:
        command:
          regex: '^\s*(ls|cat|pwd|echo|whoami|date|uname|df|head|tail|wc)(\s+[^;&|<>$`()\\]*)?\s*$'
    then:
      decision: allow
      reason: safe read-only command
  - id: approve-other-shell
    when: { target: shell_exec }
    then:
      decision: require_approval
      reason: non-safe shell command needs approval
```

See [`examples/policies/shell.yaml`](https://github.com/rebuno/rebuno/blob/main/examples/policies/shell.yaml) and
[`examples/rebuno.dev.yaml`](https://github.com/rebuno/rebuno/blob/main/examples/rebuno.dev.yaml) for working bundles.
